# Alexa Tier 2 compatibility gate: BLOCKED

Verified against current official documentation on 2026-09-18. The developer reports 5C live and verified. This is a documentation-based compatibility decision, not a failed live Cognito/Alexa experiment. No AWS resources, users, credentials, or Add-on configuration were accessed or changed for this review.

## Incompatible requirement: discovery and issuer composition

The requested architecture preserves the VoxOps Tier 1 issuer and adds Cognito as a separate Tier 2 issuer. The documented discovery contract does not establish a supported configuration for that combination. Implementation stops at the user's hard compatibility gate. This does not claim that Cognito lacks OAuth user flows or can never work with Alexa.

### Alexa evidence

The [MCP quickstart, Authentication checklist](https://www.developer.amazon.com/docs/alexaplus/add-ons/mcp-toolkit-quickstart.html) requires public protected-resource metadata, authorization-server metadata at `/.well-known/oauth-authorization-server`, and advertised `S256` support. It requires `resource` on authorization and code-exchange requests and Bearer credentials in headers. It lists OIDC authentication and WWW-Authenticate challenges as unsupported.

The [account-linking guide, Step 1](https://www.developer.amazon.com/docs/alexaplus/add-ons/mcp-toolkit-account-linking.html) says Alexa selects only the first `authorization_servers` entry. Its setup discovers endpoints rather than asking for their URLs. The [authentication guide](https://developer.amazon.com/docs/alexaplus/add-ons/mcp-toolkit-authentication.html) shows one issuer/token endpoint advertising the service and user grants; it does not describe separate issuer selection for the two tiers.

### Cognito limitation and evidence boundary

AWS's [federation endpoint inventory](https://docs.aws.amazon.com/cognito/latest/developerguide/federation-endpoints.html) documents genuine discovery at the user-pool issuer's `/.well-known/openid-configuration`, with authorization/token endpoints on its managed-login domain. It does not document the required OAuth metadata endpoint or an Alexa discovery fallback. OIDC discovery metadata is distinct from selecting OIDC as an account-linking mode; the latter's exclusion alone would not prove incompatibility. The missing documented discovery bridge is the blocker. No live endpoint probe was performed, and absence from documentation is not presented as an observed HTTP failure.

Listing VoxOps first leaves the existing service-only server selected; listing Cognito first does not document how Alexa discovers the unchanged VoxOps service issuer. This is an architectural inference from the first-entry rule, not an assertion about undocumented Alexa behavior. Pointing VoxOps metadata at Cognito endpoints while claiming a VoxOps issuer would not establish correct Cognito issuer semantics. No metadata shim, code proxy, token rewriting, or custom code/refresh store is introduced.

Moving both tiers to Cognito would change the required architecture and still encounters its documented [lack of M2M resource binding](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-define-resource-servers.html). That limitation must not be confused with its supported user resource binding.

No Alexa CLI command was run.

## Smallest realistic alternative

First request an official supported Cognito configuration from Amazon covering genuine metadata discovery (including `S256`), independent Tier 1/Tier 2 issuer selection, Tier 2 client authentication, and code-exchange resource handling. Confirmation could unblock the intended small design without another runtime component.

If that combination is unsupported, separately evaluate a maintained authorization service that natively provides one issuer for both grants, compatible discovery, and resource-bound tokens. That would require explicit approval to replace Tier 1 and fresh compatibility verification. No alternative vendor is claimed compatible here. Do not grow VoxOps into an OAuth provider.

## Hackathon recommendation and exit criteria

Keep the verified 5C boundary: remote discovery works and service-token tool execution stays forbidden. Demonstrate repository reads through the existing local/IAM-authorized workflow until user authorization is resolved. Milestone 6 should begin with compatibility clarification and a reviewed interoperability plan, not Add-on deployment.

After compatibility is established, verify code exchange and refresh with exact audience binding, register every real Alexa callback, then test a read-only user-token call. Only a deliberately provisioned demo user would be authorized to repositories accessible to the developer's GitHub App; that proposed model is not production multi-tenancy and is not implemented now.

There is no 5D deployment, demo-user command, PKCE helper, refresh test, user-token verifier, or user-token MCP smoke mode to run. Existing 5C code, IAM, metadata, routes, costs, and tests remain unchanged. No Cognito decision ADR is created.
