# VoxOps jury and interview preparation

These are concise talking points for the developer, not claims that the official Alexa Add-on has been deployed. Use the [live demo](https://d190htydn0gfle.cloudfront.net/) and [technical walkthrough](technical-walkthrough.md) as evidence.

| Likely question                               | Factual answer                                                                                                                                                                                                                                                                          |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| What problem does VoxOps solve?               | Repository state is spread across commits, issues, PRs, and CI. VoxOps lets a developer ask one question and see a sourced summary plus the exact live tool activity.                                                                                                                   |
| Why Alexa+?                                   | A voice-first assistant is useful when a developer wants a quick status without navigating several GitHub pages. The hackathon allows a self-hosted MCP server and an optional simulated web experience. This submission demonstrates those; it is not an official Alexa Add-on.        |
| Why MCP?                                      | MCP gives clients discoverable, typed, read-only tools. The same live server is used by the web simulation and can be tested independently with an MCP client.                                                                                                                          |
| Why not call GitHub directly from the model?  | The model only chooses from four MCP tools. The MCP server owns repository validation, the public-only check, GitHub calls, and safe error mapping.                                                                                                                                     |
| Why public repositories only?                 | The demo has no user identity. Reading private repositories would require per-user authorization and careful credential handling.                                                                                                                                                       |
| Why read-only?                                | Status questions need no mutation. No write permission or confirmation workflow exists, so a write tool would be misleading and unsafe.                                                                                                                                                 |
| Why no account linking?                       | Every caller sees the same public repository. Account linking would not add value to this scope, and Alexa OAuth compatibility was not verified end to end.                                                                                                                             |
| Why two Lambdas?                              | The Runtime Lambda uses HTTP API payload v2 for MCP. The Chat Lambda uses Lambda response streaming. Keeping them separate preserves a working MCP path and a true streamed answer.                                                                                                     |
| Why HTTP API plus REST API?                   | AWS currently supports API Gateway response streaming for REST APIs, not HTTP APIs. HTTP API is sufficient for MCP and health; REST API provides `STREAM` for chat.                                                                                                                     |
| Why Bedrock and Nova Micro?                   | Bedrock is the AWS model runtime. The EU Nova Micro inference profile provides a small, working model for short repository questions with tool use and streaming.                                                                                                                       |
| Why AI SDK?                                   | `streamText`, tool execution, SSE conversion, and the React client interoperate without a custom streaming protocol.                                                                                                                                                                    |
| How do you prevent invented repository state? | The first model step requires a tool decision, tool results come from live public GitHub data, and the system message instructs the model to say when data is unavailable. Language models can still summarize imperfectly, so the UI shows tool activity and context for verification. |
| How do you prevent writes?                    | There are no write tools, GitHub requests are anonymous reads, and AWS roles contain no GitHub credentials.                                                                                                                                                                             |
| How do you control cost?                      | The REST chat stage throttles at 2 requests/second with burst 2; model steps, tool calls, output tokens, request size, and retries are bounded. Lambdas have no provisioned or reserved concurrency. This is best effort, not a hard billing cap; account budgets are separate.         |
| What if GitHub fails?                         | The MCP tool returns a fixed unavailable or rate-limit message. The browser does not receive raw Octokit diagnostics.                                                                                                                                                                   |
| What if Bedrock fails?                        | The chat endpoint returns a generic unavailable response or a sanitized stream error. It does not expose AWS details or stack traces.                                                                                                                                                   |
| What did you personally design?               | I chose the public read-only scope, the MCP tool set, the split API architecture, the allowlist and IAM boundaries, and the judge-facing experience. I reviewed the implementation and manually tested the deployed flow.                                                               |
| Where did AI coding tools help?               | Codex assisted with implementation, tests, documentation, and code review. I made the product/security decisions and verified the live behavior. I do not claim every line was handwritten.                                                                                             |
| What was hardest?                             | Getting genuine incremental Bedrock responses through Lambda and API Gateway while preserving the existing MCP endpoint. It required a separate REST `STREAM` integration and AI SDK UI-message stream handling.                                                                        |
| What did you remove?                          | The demo no longer carries GitHub App, Secrets Manager, custom OAuth, private repository, or buffered-chat code. The final code keeps only the public tools and streaming path needed for judging.                                                                                      |
| What would you build next?                    | After the hackathon, only if user demand justifies it: verified Alexa Add-on integration and user-authorized repository access. They are not part of this submission.                                                                                                                   |
| What would private repositories require?      | A verified user identity, Alexa-compatible OAuth/account linking, GitHub access tied to that user, consent, token storage/rotation, and tests proving one user cannot see another's repositories.                                                                                       |
| What would writes require?                    | Narrow GitHub write permissions, explicit confirmation for each action, idempotency, audit records, and rollback/recovery design.                                                                                                                                                       |
| How would you productionize authentication?   | Start from the actual Alexa Add-on authentication contract and test issuer, resource binding, metadata, PKCE, refresh, and service credentials end to end. Do not assume Cognito alone satisfies both user and machine flows.                                                           |
| What did Alexa tooling teach you?             | Open MCP made the core testable without a proprietary simulator. Add-on CLI access and authentication documentation introduced real onboarding uncertainty, so I made the simulated experience clearly labeled rather than claiming unverified interoperability.                        |

Before an interview, verify the demo URL, GitHub license detection, MCP protocol smoke, and latest CI status. The final `GET /mcp` compliance route must be manually deployed and checked before claiming complete Streamable HTTP conformance.
